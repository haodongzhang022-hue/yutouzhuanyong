# V2 框架蓝本 · 00 · 粗纲：总体架构与分层

> 面向 **AP Physics 1 / Physics Bowl D1 专项练习系统** 的框架完善与基建文档。
> 目标：把当前"可用原型"提升为**可演进、可观测、可多人并行开发**的生产级框架。
> 设计方法论：**先粗纲 → 功能模块 → 细纲**；配套团队规模设计见 `docs/team/team_scaling.md`。

---

## 1. 一句话定位

从「采集入库 + API + 一次性专项卷脚本」升级为 **「数据采集 → 规范化组织 → 专项卷生产 → 练习服务 → 观测运维」五段式** 的闭环平台。

核心不变式：**一份题 = 一份可溯源、可被组织、可被消费的资产**；
且"机器可读的规范化 JSON"与"人类可读的专项卷"由**同一 Schema 与知识点目录**绑定，永不脱节（承接 V1 既有成果）。

| 能力 | V1 状态 | 缺口（V2 要补） |
|------|--------|----------------|

## 3. V2 分层架构（粗纲：五层 + 横向三件套）

```
┌───────────────────────────────────────────────────────────────────┐
│  L5  应用/产品层   专项练习应用  错题本  学习计划  成绩/统计       │
├───────────────────────────────────────────────────────────────────┤
│  L4  服务接口层    REST API（统一错误/鉴权/限流）+ 静态卷服务      │
├───────────────────────────────────────────────────────────────────┤
│  L3  领域组织层    规范化  知识点目录  双向索引  专项卷渲染         │
├───────────────────────────────────────────────────────────────────┤
│  L2  采集存储层    采集器  去重入库  Schema/迁移  只读派生          │
├───────────────────────────────────────────────────────────────────┤
│  L1  基础支撑层    配置中心  路径  日志  工具                       │
└───────────────────────────────────────────────────────────────────┘
   ┌─────────────┬─────────────┬──────────────┐
   │ 观测(日志/指标) │ 配置(分级/校验) │ 生命周期(启动/优雅停机) │  ← 横向三件套
   └─────────────┴─────────────┴──────────────┘
```

**分层原则**
1. **单向依赖**：上层只能依赖下层，禁止反向；同层通过接口横向协作。
2. **依赖注入(DI)**：去掉 `src/api/server.py` 里的模块级全局 `db/fetch_service`，改为工厂/容器注入，消除"测试难、多实例难"。
3. **接口稳定**：`L2→L3` 只认规范化字段；`L4` 只认 `L3` 聚合结果；Schema 是各层间唯一数据契约。
4. **只读派生**：组织/专项卷/索引一律是 `data/builtin` + DB 的**只读派生**，可随时重建，不回写采集源。

## 4. 横向三件套（可用性基石）

### 4.1 配置中心（L1 + config/settings.yaml）
- 分层覆盖：`默认值 < settings.yaml < 环境变量 < CLI 参数`。
- 启动即校验：考试枚举、调度时间、源必填字段，非法直接拒绝启动并给可读报错。
- 敏感项（token/密码）仅走环境变量，不进配置文件。

### 4.2 观测体系（横切）
- **结构化日志**：统一 `key=value` 字段（request_id、exam、source、耗时），区分 info/warn/error。
- **健康分级**：`/api/health/live`（进程活着）、`/api/health/ready`（依赖就绪：DB 可连、目录可写）。
- **指标端点** `/api/metrics`：采集成功/失败数、库内题量、最近一次调度时间戳（Prometheus 可抓）。
- **审计留痕**：采集日志、组织重建日志、作答日志均落 `logs/` + 可选入库。

### 4.3 生命周期
- `start()` 顺序：载配置→校验→建目录→连 DB(迁移)→预热采集器→注册调度→起 API。
- 优雅停机：收到 SIGINT/SIGTERM → 停调度→排空在途请求→落盘→关连接，窗口默认 10s。
- 以 `src/main.py` 为唯一入口编排，`run.sh` 只转发命令。

## 5. 关键设计决策（D/R 记录）

| # | 决策 | 理由 | 影响面 |
|---|------|------|--------|
| D1 | 新增统一 `src/core/` 基础设施包（config/log/metrics/lifecycle） | 横切逻辑集中，去重 | L1~L5 |
| D2 | 模块级全局态改为 `create_app(deps)` 工厂注入 | 可测试/可多实例/隔离 | L4 |
| D3 | DB 增加 `kp_code/type_codes/norm_qid` 冗余索引列 + schema_version | 组织层免全量重扫、可增量 | L2/L3 |
| D4 | 专项卷改为"版本化产物 + 增量重建触发器" | 采集新题自动刷新，可回溯 | L3/调度 |
| D5 | 组织层接入采集管线（fetch 成功后回调 rebuild） | 数据变化即时反映到卷 | L2→L3 |
| D6 | 采集器统一"超时+重试+源级降级"，源失败不拖垮整批 | 提升可用性 | L2 |
| D7 | 新增作答记录/错题本/计划表（L5 数据底座） | 从"取题"到"练习闭环" | DB/应用 |
| D8 | 专项卷目录 & 版本入库表，供 API 稳定访问 | 卷可寻址/可版本 | L3/L4 |

## 7. 里程碑建议（供经理切开发节奏）

- **M0 基建落地**：M7+M6（框架、配置、观测、生命周期）→ 先夯实地基。
- **M1 采集加固**：M1（重试/幂等/健康）+ M8 源管理。
- **M2 组织闭环**：M2+M3（增量重建、版本化、HTML）。
- **M3 练习闭环**：M4+M5（作答/错题/计划 + API）。
- **M4 上线打磨**：全链路测试、部署、压测、灰度。

> 每模块是**可独立指派、可独立验收**的工作单元；模块内细分工（开发/测试/文档）见团队文档。
